Phase 2 completed

Phase 2 marked the point where this project shifted from a simple frontend build into a full-stack platform with production-grade engineering practices. In this phase, I focused on backend integration, authentication and authorisation, secure configuration management, database design, and deployment-ready architecture. The entries below capture the key systems I implemented/researched, the technical challenges I ran into, and the practical lessons that shaped the current direction of Xenon Dev.

As the project evolved from a small into a more complex, multi layered system, I reached a point where informal tracking simply wasn’t sustainable. Progress became harder to monitor, and on several occasions I even duplicated work because I couldn’t easily locate previously implemented methods. It was a clear sign that the project had outgrown ad hoc organisation.

To address this, I introduced structured project management practices directly within GitHub. Creating issues and project boards transformed my workflow by giving me:
1. A reliable, transparent way to track progress and maintain momentum.
2. A space to apply the delivery discipline I developed at Alchemy Technology Services.
3. A foundation for a consistent, maintainable branching strategy.

This shift significantly improved the quality and predictability of my development process. Below is the branching strategy currently used in the project, reflecting the level of rigour I apply to code quality:

main – The production branch. Only code that has been tested multiple times makes it here. It is linked to AWS and deployed using CI/CD pipelines.

Dev – The last line of defence. Like main, it is linked to AWS and deployed via CI/CD, but the hosted site is not public-facing — it exists strictly for development and QA testing. Any feature destined for production is validated here first.

dependency_updates – A dedicated branch for managing frequent framework updates (Angular and Spring Boot), ensuring they remain isolated and controlled.

small-changes – Reserved for minor, low-risk changes that I want on production quickly without bypassing proper protocol.

Backend-Integration – The branch I am currently working on. It has been a major focus for several months and has deepened my understanding of backend architecture, API design, and full‑stack integration.

Spring Security was a complex topic to learn and wrap my head around, but it is incredibly powerful when used correctly. I first encountered it through a Spring Boot course on Udemy by Chad Darby — and as a side note, Chad is a fantastic instructor if you're looking to get into full-stack development. Highly recommended.

The first learning curve was truly understanding what a filter chain is and what happens under the hood. A basic, bare-bones filter configuration would look something like this: 

                  
                  import org.springframework.context.annotation.Bean;
                  import org.springframework.context.annotation.Configuration;
                  import org.springframework.security.config.annotation.web.builders.HttpSecurity;
                  import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
                  import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
                  import org.springframework.security.web.SecurityFilterChain;

                  @Configuration // Marks this class as a source of bean definitions for the application context
                  @EnableWebSecurity // Enables Spring Security's web security support
                  public class SecurityConfig {{ '{' }}

                      @Bean // Indicates that this method produces a bean to be managed by the Spring container
                      public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {{ '{' }}

                          http
                              /* 
                                ---------------------------------------------------------------
                                  CSRF PROTECTION
                                  Enabled by default. Protects state-changing requests (POST,
                                  PUT, DELETE) from cross-site request forgery attacks by
                                  requiring a hidden token in forms.
                                  Disable only for stateless REST APIs (using JWTs, etc.).
                                ---------------------------------------------------------------
                              */ 
                              .csrf(AbstractHttpConfigurer::disable)

                              /*
                                  ---------------------------------------------------------------
                                    AUTHORIZATION RULES
                                    Processed by FilterSecurityInterceptor (or, in modern Spring
                                    Security, AuthorizationFilter) at the END of the chain.
                                    Rules are evaluated top-to-bottom — put specific rules first.
                                
                                    AnonymousAuthenticationFilter runs just before this block:
                                    if no auth has been set by the earlier filters, it assigns
                                    an "anonymous" token so the principal is never null.
                                  ---------------------------------------------------------------

                              .authorizeHttpRequests(requests -> requests
                                  // Public pages — anyone (including anonymous) can access
                                  .requestMatchers("/", "/welcome", "/css/**", "/js/**").permitAll()                

                                  // Any authenticated user (not anonymous)
                                  .anyRequest().authenticated()  
                                  
                              );            

                          return http.build(); // build the SecurityFilterChain

                          /*
                              Note: We don't configure CorsConfiguration, implement role-based 
                              access control, or any authentication, because those topics will be
                              demonstrated in other sections.
                          */
                      {{ '}' }}
                      
                  {{ '}' }}

One of Spring Security's most valuable capabilities is the ability to define multiple, independent filter chains, each with distinct matchers, rules, and behavior. During this phase, I explored whether a custom filter was needed to address what I initially considered a security gap. At the time, I had recently improved my understanding of how bearer tokens relate to Keycloak sessions: the authorization code flow establishes authentication, and tokens are then presented on subsequent API requests. My concern was that I had not explicitly added backend token checks, so I investigated implementing manual validation inside a custom filter. 

                  
                  // 1. Create a custom filter by implementing the Filter interface
                  @Component
                  public class CustomFilter implements Filter {{ '{' }}
                  /* 
                      Filter interface is a part of the Java Servlet API and is used to 
                      perform filtering tasks on either the request to a resource, the 
                      response from a resource, or both.
                  */
                      private final Keycloak_Service_Impl keycloakService;
                      
                      public CustomFilter(Keycloak_Service_Impl keycloakService) {{ '{' }}
                          this.keycloakService = keycloakService;
                      {{ '}' }}

                      // doFilter method is where you implement the logic to validate the incoming request
                      @Override
                      public void doFilter(ServletRequest request, ServletResponse response, FilterChain filterChain)
                              throws IOException, ServletException {{ '{' }}

                          HttpServletRequest httpRequest = (HttpServletRequest) request;
                          HttpServletResponse httpResponse = (HttpServletResponse) response;

                          String token = httpRequest.getHeader("Token");

                          // Validate the incoming request
                          // If the token is missing or invalid, reject the request
                          // note: the actual validation logic should be implemented in the Keycloak_Service_Impl class        
                          if (token == null || !keycloakService.validateToken(token)) {{ '{' }}
                              httpResponse.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
                              httpResponse.setContentType("application/json");
                              httpResponse.getWriter().write("{{ '{' }}\"error\": \"Invalid or missing Token\"{{ '}' }}");
                              return; // tells the filter to stop here and not to continue with the filter chain 
                                      // (sends a 401 response back to the client)
                          {{ '}' }}

                          // Valid — pass the request along the filter chain
                          filterChain.doFilter(request, response);
                      {{ '}' }}
                  {{ '}' }}
                
              
                  
                    // 2. Register it in the Security Config
                    @Configuration
                    @EnableWebSecurity
                    public class SecurityConfig {{ '{' }}

                        @Autowired
                        private CustomFilter customFilter;

                        @Bean
                        public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {{ '{' }}
                            http
                                .csrf(csrf -> csrf.disable())
                                .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
                                .addFilterBefore(customFilter, UsernamePasswordAuthenticationFilter.class);

                            return http.build();
                        {{ '}' }}
                    {{ '}' }}

In conclusion, this investigation clarified an important design principle: custom filters should be introduced only when they add clear value beyond the framework's built-in capabilities. For standard JWT validation with Keycloak, Spring Security's resource server support already provides the required request protection. This investigation still proved useful, as it strengthened my understanding of filter ordering, authentication flow, and when custom security components are genuinely justified.

Cross-Origin Resource Sharing (CORS) became a critical topic as soon as the frontend and backend began communicating across different origins. While I had encountered CORS previously, the practical implementation became clear only after debugging browser errors during local integration. By default, the browser's same-origin policy blocks requests from one origin (for example, http://localhost:4200) to another (for example, http://localhost:8443/api) unless the server explicitly returns the correct CORS headers.

In Spring Security, CORS is processed before authentication filters. This ordering is essential because browsers send a preflight OPTIONS request before the actual request. That preflight must return 200 OK; if it is rejected with 401 Unauthorized, the browser blocks the call before the application logic is reached. The straightforward approach is to define CorsConfiguration in the security filter chain: 

                  
                  @Bean
                  public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {{ '{' }}
                      http
                              .csrf(csrf -> csrf.disable())
                              .authorizeHttpRequests(auth -> auth.anyRequest().permitAll());

                      CorsConfiguration corsConfig = new CorsConfiguration();

                      // Allowed origins — lock this down to real domains in production
                      corsConfig.setAllowedOrigins(List.of(
                              "http://localhost:4200" // Angular dev server
                      ));

                      // HTTP methods the browser is allowed to use
                      corsConfig.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));

                      // Headers the browser may send (Authorization carries the JWT)
                      corsConfig.setAllowedHeaders(List.of("Authorization", "Content-Type"));

                      // Allow the browser to read the Authorization header in responses
                      corsConfig.setExposedHeaders(List.of("Authorization"));

                      // Required when the frontend sends cookies or Authorization headers
                      corsConfig.setAllowCredentials(true);

                      // register the CORS configuration for all endpoints
                      http.cors(cors -> cors.configurationSource(request -> corsConfig));

                      return http.build();
                  {{ '}' }}

One early mistake was configuring allowedOrigins("*") together with allowCredentials(true). These settings are incompatible: when credentials are enabled, browsers reject wildcard origins. The correct solution is to specify explicit trusted origins per environment. Establishing this pattern also improved how environment-specific configuration is managed across the project.

Sensitive configuration is managed with environment variables, and local secrets are kept out of source control. This approach aligns with best practice by preventing accidental exposure of credentials and server configuration details.

JSON Web Tokens (JWTs) are the mechanism the project uses to prove identity across the boundary between the Angular frontend, the Spring Boot API, and Keycloak. A JWT is a compact, URL-safe string made up of three Base64URL-encoded parts separated by dots: a header (algorithm metadata), a payload (claims about the user), and a signature (cryptographic proof that the token hasn't been tampered with).

In this project, Keycloak issues the tokens. The Angular app obtains an access token after the user logs in and attaches it to every API request as a Bearer token in the Authorization header. The Spring Boot resource server then validates the token without contacting Keycloak on every request — it does this by fetching Keycloak's public keys from the JWKS endpoint once and caching them locally. Configuring the resource server requires only a single property pointing at the issuer URI: 

                  
                  # application.properties
                  spring.security.oauth2.resourceserver.jwt.issuer-uri=\
                      http://localhost:8080/realms/Xenon-Dev-DEV-ENV

                  # Spring auto-discovers the JWKS URI from the issuer's
                  # OpenID Connect discovery document at:
                  # {{ '{' }}issuer-uri{{ '}' }}/.well-known/openid-configuration

On the Spring side, enabling JWT validation in the filter chain is then just one line: 

                  
                  .oauth2ResourceServer(oauth2 -> oauth2
                      .jwt(jwt -> jwt
                          // Optional: customise how claims are mapped to Spring's
                          // GrantedAuthority list (e.g. extracting Keycloak realm roles)
                          .jwtAuthenticationConverter(keycloakJwtAuthenticationConverter())
                      )
                  )

One thing worth noting is that JWTs are stateless. The server never stores them — which means revoking a token before it expires requires extra work (a token blacklist or short expiry windows). For this project I settled on short-lived access tokens (5 minutes) combined with Keycloak's refresh token flow, which strikes a reasonable balance between security and usability.

A foundational principle of secure backend development is that secrets must never be embedded in source code. Despite how self-evident this may appear, it is a surprisingly common mistake to include a database password or API key directly in an application.properties file and commit it to version control. A deliberate configuration strategy was established from the outset of the Xenon Dev project to prevent this entirely.

The approach is layered. In local development, sensitive values are stored in an application-local.properties file that is listed in .gitignore and excluded from all commits. Spring Boot is configured to activate the local profile automatically during development, resolving these values without requiring any modifications to tracked files. In deployed environments, credentials are provided exclusively as environment variables injected by AWS, keeping them entirely outside the repository: 

                  
                  # application.properties (committed — no secrets here)
                  spring.datasource.url=${DB_URL}
                  spring.datasource.username=${DB_USERNAME}
                  spring.datasource.password=${DB_PASSWORD}

                  keycloak.client-secret=${KEYCLOAK_CLIENT_SECRET}                  

                  # -----------------------------------------------------------
                  # application-local.properties (git-ignored — secrets live here locally)
                  # -----------------------------------------------------------
                  # spring.datasource.url=jdbc:mysql://localhost:3306/xenon_dev
                  # spring.datasource.username=root
                  # spring.datasource.password=supersecret
                  # keycloak.client-secret=abc123...

The Keycloak client secret warrants particular attention. In OAuth2, the client secret is the credential the backend presents to Keycloak when exchanging an authorisation code for a token, or when authenticating via the client credentials flow for service-to-service communication. Exposure of this value would allow an attacker to impersonate the backend application entirely. It is therefore treated with the same rigour as a database password: stored outside version control.

Designing a clean REST API is harder than it looks. I started with a rough set of endpoints that "got the job done" but quickly realised they were inconsistent, hard to document, and awkward for the Angular frontend to consume. Taking a step back and applying RESTful conventions properly made an enormous difference to the maintainability of the project.

The core principle is that URLs represent resources (nouns), not actions (verbs). HTTP methods carry the action semantics. Below is an example of the controller structure used for the user resource in this project: 

                  
                  @RestController
                  @RequestMapping("/api/users")
                  public class UserController {{ '{' }}

                      // GET /api/users          — list all users (paginated)
                      @GetMapping
                      public Page<UserDTO> getUsers(Pageable pageable) {{ '{' }}
                          return userService.findAll(pageable);
                      {{ '}' }}

                      // GET /api/users/{id}    — get a single user by ID
                      @GetMapping("/{id}")
                      public UserDTO getUser(@PathVariable Long id) {{ '{' }}
                          return userService.findById(id);
                      {{ '}' }}

                      // POST /api/users         — create a new user
                      @PostMapping
                      @ResponseStatus(HttpStatus.CREATED) // 201 Created, not 200 OK
                      public UserDTO createUser(@RequestBody @Valid CreateUserRequest request) {{ '{' }}
                          return userService.create(request);
                      {{ '}' }}

                      // PUT /api/users/{id}    — replace a user (idempotent)
                      @PutMapping("/{id}")
                      public UserDTO updateUser(@PathVariable Long id,
                                               @RequestBody @Valid UpdateUserRequest request) {{ '{' }}
                          return userService.update(id, request);
                      {{ '}' }}

                      // DELETE /api/users/{id} — remove a user
                      @DeleteMapping("/{id}")
                      @ResponseStatus(HttpStatus.NO_CONTENT) // 204, no body
                      public void deleteUser(@PathVariable Long id) {{ '{' }}
                          userService.delete(id);
                      {{ '}' }}
                  {{ '}' }}

A few conventions I adopted across the whole API: always return DTOs rather than JPA entities directly (covered in its own section), use meaningful HTTP status codes (201 for created, 204 for deleted, 404 with a consistent error body for not found), and version the API in the URL path (/api/v1/...) from the very beginning — it is far easier to version upfront than to retrofit it later when the Angular frontend already depends on a dozen endpoints.

Debugging a REST API involves a different mindset to debugging a monolithic application. The problem could be anywhere in the chain: the Angular HTTP client, the network, the Spring Security filter, the controller, the service, or the database. Over the course of building this project I built up a systematic approach to narrowing down where things are going wrong quickly.

My primary tool is Postman. By firing requests directly at the API (bypassing the Angular app entirely), I can immediately eliminate the frontend as the source of the problem. Postman also handles OAuth2 flows natively, so I can obtain a real Keycloak token and attach it to requests without writing a single line of code. For logging on the Spring side, I enable detailed request/response logging through a custom OncePerRequestFilter: 

                  
                  @Component
                  public class RequestLoggingFilter extends OncePerRequestFilter {{ '{' }}

                      private static final Logger log =
                          LoggerFactory.getLogger(RequestLoggingFilter.class);

                      @Override
                      protected void doFilterInternal(HttpServletRequest request,
                                                      HttpServletResponse response,
                                                      FilterChain filterChain)
                              throws ServletException, IOException {{ '{' }}

                          long start = System.currentTimeMillis();

                          try {{ '{' }}
                              filterChain.doFilter(request, response);
                          {{ '}' }} finally {{ '{' }}
                              long duration = System.currentTimeMillis() - start;
                              log.info("[{}] {} {} -> {} ({}ms)",
                                  request.getRemoteAddr(),
                                  request.getMethod(),
                                  request.getRequestURI(),
                                  response.getStatus(),
                                  duration);
                          {{ '}' }}
                      {{ '}' }}
                  {{ '}' }}

For Spring Security specifically, the most useful debugging property is logging.level.org.springframework.security=TRACE. This floods the console with output, but it shows exactly which filters ran, which ones voted, and why a request was ultimately permitted or denied. I only enable it locally when actively investigating a security-related issue — leaving it on in any other environment would be a confidentiality risk. Pairing this with the browser's Network tab to inspect the raw request and response headers gives a complete picture of what is happening at every layer.

Identity and Access Management (IAM) is the discipline of deciding who can do what on which resource. In this project, IAM is implemented through a combination of Keycloak (which handles authentication and issues JWTs carrying identity claims) and Spring Security (which enforces authorisation rules on each endpoint based on those claims).

The critical bridge between the two is the JWT authentication converter. Keycloak encodes the user's roles inside the token under a non-standard claim path (realm_access.roles), whereas Spring Security expects GrantedAuthority objects prefixed with ROLE_. Without a custom converter, Spring simply wouldn't see any roles in the token and would deny every role-restricted endpoint. The converter unwraps the Keycloak claim and maps it to Spring's format: 

                  
                  @Component
                  public class KeycloakJwtAuthenticationConverter
                          implements Converter<Jwt, AbstractAuthenticationToken> {{ '{' }}

                      private final JwtGrantedAuthoritiesConverter defaultConverter =
                          new JwtGrantedAuthoritiesConverter();

                      @Override
                      public AbstractAuthenticationToken convert(Jwt jwt) {{ '{' }}
                          // Extract standard scopes (e.g. SCOPE_openid) via the default converter
                          Collection<GrantedAuthority> authorities =
                              new ArrayList<>(defaultConverter.convert(jwt));

                          // Extract Keycloak realm roles from realm_access.roles
                          Map<String, Object> realmAccess =
                              jwt.getClaimAsMap("realm_access");

                          if (realmAccess != null && realmAccess.containsKey("roles")) {{ '{' }}
                              List<?> roles = (List<?>) realmAccess.get("roles");
                              roles.stream()
                                  .map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                                  .forEach(authorities::add);
                          {{ '}' }}

                          return new JwtAuthenticationToken(jwt, authorities,
                              jwt.getClaimAsString("preferred_username"));
                      {{ '}' }}
                  {{ '}' }}

With this converter in place, the JWT arriving from Keycloak is fully understood by Spring Security. Downstream, the controller can use standard Spring annotations such as @PreAuthorize("hasRole('ADMIN')") to enforce fine-grained access control, and the identity of the authenticated user is available anywhere in the request via the SecurityContextHolder — without any additional calls to Keycloak.

Role-based access control (RBAC) is the layer on top of authentication that answers the question: "this user is who they say they are — but are they allowed to perform this action?" In this project, roles are defined in Keycloak and embedded in the JWT, then enforced in Spring Security at both the HTTP layer (filter chain rules) and the method layer (@PreAuthorize annotations).

The project currently defines three roles: USER (standard authenticated user), MODERATOR (elevated read access and the ability to manage content), and ADMIN (full access including user management endpoints). Applying these rules at the filter chain level covers the coarse-grained cases, while @PreAuthorize handles fine-grained method-level security: 

                  
                  // --- Filter chain (coarse-grained) ---
                  .authorizeHttpRequests(auth -> auth
                      .requestMatchers(HttpMethod.GET, "/api/v1/**").hasAnyRole("USER", "MODERATOR", "ADMIN")
                      .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
                      .requestMatchers("/api/v1/moderation/**").hasAnyRole("MODERATOR", "ADMIN")
                      .anyRequest().authenticated()
                  )

                  // --- Method-level (fine-grained) ---
                  @Service
                  public class UserManagementService {{ '{' }}

                      // Only admins can delete users
                      @PreAuthorize("hasRole('ADMIN')")
                      public void deleteUser(Long userId) {{ '{' }}
                          userRepository.deleteById(userId);
                      {{ '}' }}

                      // A user can read their own profile; an admin can read any profile
                      @PreAuthorize("hasRole('ADMIN') or #username == authentication.name")
                      public UserDTO getProfile(String username) {{ '{' }}
                          return userRepository.findByUsername(username)
                              .map(userMapper::toDTO)
                              .orElseThrow(() -> new ResourceNotFoundException("User not found"));
                      {{ '}' }}
                  {{ '}' }}

The @PreAuthorize expression on getProfile above demonstrates Spring's SpEL-based security expressions. The #username == authentication.name clause binds the method parameter to the currently authenticated principal — a clean way to enforce ownership rules without writing any conditional logic inside the method body itself. Enabling method security requires adding @EnableMethodSecurity to the security configuration class.

One of the more experimental features in the backend integration branch is a lightweight AI agent task management system. The idea is that certain long-running or ambiguous tasks can be delegated to an AI agent (backed by an LLM API), which then breaks them down into sub-tasks, executes them asynchronously, and reports progress back to the application. This is an emerging architectural pattern often called an agentic loop.

In practice the implementation is straightforward: each agent task is persisted as a database record with a status field (PENDING, IN_PROGRESS, COMPLETED, FAILED). A Spring @Async service picks up pending tasks, calls the LLM API, updates the record, and emits a Server-Sent Event so the Angular frontend can show live progress. Below is the core task entity and the async execution flow: 

                  
                  @Entity
                  @Table(name = "agent_tasks")
                  public class AgentTask {{ '{' }}

                      @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
                      private Long id;

                      @Column(nullable = false)
                      private String prompt;         // The instruction given to the agent

                      @Enumerated(EnumType.STRING)
                      private TaskStatus status = TaskStatus.PENDING;

                      @Column(columnDefinition = "TEXT")
                      private String result;          // LLM response stored on completion

                      private LocalDateTime createdAt = LocalDateTime.now();
                      private LocalDateTime completedAt;
                      // ... getters / setters
                  {{ '}' }}

                  // --- Async execution service ---
                  @Service
                  public class AgentTaskService {{ '{' }}

                      @Async
                      public CompletableFuture<Void> executeTask(AgentTask task) {{ '{' }}
                          task.setStatus(TaskStatus.IN_PROGRESS);
                          agentTaskRepository.save(task);

                          try {{ '{' }}
                              String result = llmClient.complete(task.getPrompt()); // call LLM
                              task.setResult(result);
                              task.setStatus(TaskStatus.COMPLETED);
                          {{ '}' }} catch (Exception e) {{ '{' }}
                              task.setStatus(TaskStatus.FAILED);
                          {{ '}' }} finally {{ '{' }}
                              task.setCompletedAt(LocalDateTime.now());
                              agentTaskRepository.save(task);
                              sseEmitterService.broadcast(task); // push update to frontend
                          {{ '}' }}

                          return CompletableFuture.completedFuture(null);
                      {{ '}' }}
                  {{ '}' }}

Using @Async with a dedicated thread pool prevents the LLM call (which can take several seconds) from blocking the request thread. The SSE emitter broadcasts the completed task to any connected Angular clients so the UI updates in real time — no polling required.

AWS Simple Email Service (SES) is the transactional email layer for this project. It handles emails like account verification, password reset links, and notification messages. I chose SES over alternatives because the project is already hosted on AWS, meaning IAM roles can be used to grant the application permission to send emails without storing long-lived API keys in the application itself (when running in a properly configured EC2 or ECS environment).

Integration is done through the AWS SDK v2 for Java. The SesClient is configured as a Spring bean, and a thin service wraps the SDK calls to keep the rest of the application decoupled from AWS specifics: 

                  
                  @Configuration
                  public class AwsSesConfig {{ '{' }}

                      @Bean
                      public SesClient sesClient(
                              @Value("${aws.ses.region}") String region,
                              @Value("${aws.ses.access-key}") String accessKey,
                              @Value("${aws.ses.secret-key}") String secretKey) {{ '{' }}

                          return SesClient.builder()
                              .region(Region.of(region))
                              .credentialsProvider(StaticCredentialsProvider.create(
                                  AwsBasicCredentials.create(accessKey, secretKey)))
                              .build();
                      {{ '}' }}
                  {{ '}' }}

                  // --- Email service ---
                  @Service
                  public class EmailService {{ '{' }}

                      private final SesClient sesClient;

                      @Value("${aws.ses.sender-address}")
                      private String senderAddress;

                      public void sendVerificationEmail(String toAddress, String verificationLink) {{ '{' }}
                          SendEmailRequest request = SendEmailRequest.builder()
                              .source(senderAddress)
                              .destination(Destination.builder()
                                  .toAddresses(toAddress)
                                  .build())
                              .message(Message.builder()
                                  .subject(Content.builder()
                                      .data("Verify your Xenon Dev account")
                                      .build())
                                  .body(Body.builder()
                                      .html(Content.builder()
                                          .data("<p>Click <a href='" + verificationLink
                                              + "'>here</a> to verify your account.</p>")
                                          .build())
                                      .build())
                                  .build())
                              .build();

                          sesClient.sendEmail(request);
                      {{ '}' }}
                  {{ '}' }}

Before SES will send emails to arbitrary addresses, the sending domain must be verified and the account must be moved out of the SES sandbox. During development, both the sender and recipient addresses need to be individually verified — a friction point worth knowing about early. In production, domain verification via a DNS TXT record unlocks sending to any address on that domain.

Spring Data JPA repositories were one of the features that made me genuinely appreciate the Spring ecosystem. At its simplest, a JPA repository is an interface that Spring implements at runtime — you declare the methods you need and Spring writes the SQL for you. No boilerplate, no manual connection management, no result-set mapping.

In the project I use a hierarchy of repository types depending on the complexity of the queries needed. JpaRepository covers the standard CRUD operations and pagination. For more complex queries I use JPQL with @Query annotations, and for the most performance-sensitive paths I drop down to native SQL: 

                  
                  @Repository
                  public interface UserRepository extends JpaRepository<User, Long> {{ '{' }}

                      // Spring derives the SQL from the method name automatically
                      Optional<User> findByEmail(String email);
                      boolean existsByUsername(String username);

                      // JPQL query — operates on JPA entities, not raw tables
                      @Query("SELECT u FROM User u WHERE u.role = :role AND u.active = true")
                      List<User> findActiveUsersByRole(@Param("role") Role role);

                      // Native SQL for a complex aggregation — bypasses the JPA entity model
                      @Query(
                          value = "SELECT u.username, COUNT(o.id) AS order_count " +
                                  "FROM users u LEFT JOIN orders o ON o.user_id = u.id " +
                                  "GROUP BY u.username " +
                                  "ORDER BY order_count DESC LIMIT :limit",
                          nativeQuery = true
                      )
                      List<Object[]> findTopUsersByOrderCount(@Param("limit") int limit);
                  {{ '}' }}

One pitfall I ran into early on was the N+1 query problem. When a JPA entity has a lazily-loaded relationship (e.g. a User has many Orders), fetching a list of 100 users and then accessing each user's orders triggers 101 queries — one for the user list and one per user. The fix is a JOIN FETCH in the JPQL query, or a @EntityGraph annotation on the repository method, which tells JPA to fetch the related data in a single query.

A Data Transfer Object (DTO) is a plain object whose sole purpose is to carry data between layers of the application. In the context of this project, DTOs sit between the JPA entities (which mirror the database schema) and the REST API (which defines the public contract). This separation solves several real problems at once: it prevents accidentally exposing sensitive fields, it decouples the API contract from the database schema, and it gives a natural place to put input validation annotations.

The project follows a convention of having separate DTOs for reads and writes — a response DTO (what the API sends out) and a request DTO (what the API accepts). Mapping between entity and DTO is done by a dedicated Mapper class rather than doing it inline in the controller or service: 

                  
                  // --- Response DTO (what the API sends to the client) ---
                  public record UserDTO(
                      Long id,
                      String username,
                      String email,
                      String role,
                      LocalDateTime createdAt
                      // Note: password hash is NOT included here
                  ) {{ '{' }}{{ '}' }}

                  // --- Request DTO (what the client sends to create a user) ---
                  public record CreateUserRequest(
                      @NotBlank(message = "Username is required")
                      @Size(min = 3, max = 30, message = "Username must be 3-30 characters")
                      String username,

                      @Email(message = "Must be a valid email address")
                      @NotBlank
                      String email,

                      @NotBlank
                      @Size(min = 8, message = "Password must be at least 8 characters")
                      String password
                  ) {{ '{' }}{{ '}' }}

                  // --- Mapper ---
                  @Component
                  public class UserMapper {{ '{' }}

                      public UserDTO toDTO(User user) {{ '{' }}
                          return new UserDTO(
                              user.getId(),
                              user.getUsername(),
                              user.getEmail(),
                              user.getRole().name(),
                              user.getCreatedAt()
                          );
                      {{ '}' }}

                      public User toEntity(CreateUserRequest request) {{ '{' }}
                          User user = new User();
                          user.setUsername(request.username());
                          user.setEmail(request.email());
                          // Password is hashed in the service layer, not here
                          return user;
                      {{ '}' }}
                  {{ '}' }}

Using Java records for DTOs (available since Java 16) keeps the code concise — the compiler generates the constructor, accessors, equals, hashCode, and toString automatically. The @Valid annotation on the controller method parameter triggers Bean Validation on the incoming request DTO, and any violation automatically produces a 400 Bad Request response with a descriptive error body — no manual validation code needed.

A MySQL view is a stored SELECT statement that acts like a virtual table. Querying a view looks identical to querying a real table, but the data is assembled on the fly from the underlying tables when the view is accessed. I introduced views in this project for two reasons: to simplify complex recurring queries that appeared in multiple places, and to provide a read-only, security-trimmed projection of data that could be exposed more freely than the raw tables.

A practical example is the v_user_order_summary view used by the admin dashboard. Rather than writing the same multi-table join every time the dashboard data is needed, the join is defined once in the view, and every subsequent query becomes a simple SELECT: 

                  
                  -- Create the view once (run as part of Flyway migration)
                  CREATE OR REPLACE VIEW v_user_order_summary AS
                  SELECT
                      u.id          AS user_id,
                      u.username,
                      u.email,
                      COUNT(o.id)   AS total_orders,
                      COALESCE(SUM(o.total_amount), 0) AS lifetime_spend,
                      MAX(o.created_at) AS last_order_date
                  FROM users u
                  LEFT JOIN orders o ON o.user_id = u.id
                  GROUP BY u.id, u.username, u.email;

                  -- Querying the view is as simple as a table read
                  SELECT * FROM v_user_order_summary
                  WHERE total_orders > 0
                  ORDER BY lifetime_spend DESC
                  LIMIT 10;

On the Spring side, views integrate cleanly with JPA by mapping them to a read-only entity annotated with @Immutable (Hibernate). This tells Hibernate never to attempt an INSERT or UPDATE against the view, which prevents confusing runtime errors. Flyway, which the project uses for schema migrations, tracks view definitions just like table definitions, keeping the view always in sync with the application code.

A MySQL trigger is a piece of SQL that the database engine executes automatically in response to an INSERT, UPDATE, or DELETE on a specified table. Triggers enforce data integrity rules at the database level — meaning they fire regardless of which application, service, or tool modifies the data. This makes them a reliable safety net for invariants that must always hold.

In this project, triggers are used for two things: maintaining an audit log (every change to a sensitive table is recorded automatically), and enforcing a soft-delete pattern that prevents hard deletes on the users table. Below is the audit log trigger used on the orders table: 

                  
                  DELIMITER $$

                  -- Fires after any UPDATE on the orders table and records
                  -- the old and new values in the audit_log table.
                  CREATE TRIGGER trg_orders_after_update
                  AFTER UPDATE ON orders
                  FOR EACH ROW
                  BEGIN
                      INSERT INTO audit_log (
                          table_name,
                          record_id,
                          action,
                          old_value,
                          new_value,
                          changed_at
                      ) VALUES (
                          'orders',
                          OLD.id,
                          'UPDATE',
                          JSON_OBJECT(
                              'status',       OLD.status,
                              'total_amount', OLD.total_amount
                          ),
                          JSON_OBJECT(
                              'status',       NEW.status,
                              'total_amount', NEW.total_amount
                          ),
                          NOW()
                      );
                  END$$

                  DELIMITER ;

One important caveat: because triggers run inside the database engine, they are invisible to the JPA layer — Hibernate has no knowledge that a trigger fired. This means the first-level cache can become stale after a triggered operation. The safest approach is to call entityManager.refresh(entity) after operations you know will fire a trigger that affects the same entity, or to structure the code so that Hibernate-managed entities and trigger-maintained data are in separate tables that never overlap in a single transaction.

Keycloak is the identity provider at the heart of the project's authentication architecture. It handles user registration, login, token issuance, token refresh, and logout — offloading all of that complexity from the application itself. Instead of building and maintaining a custom auth system (with all the security risks that entails), the Spring Boot backend acts purely as a resource server that trusts the JWTs that Keycloak signs.

Setting up Keycloak for this project involved creating a realm (a namespace for users and clients), registering the Angular app and the Spring Boot API as separate clients, and defining the realm roles that map to the application's access control model. The Angular client uses the Authorization Code + PKCE flow — the most secure flow for public clients (browser apps that cannot safely store a client secret): 

                  
                  // xenon-dev-config.ts — Keycloak connection settings (Angular)
                  export default {{ '{' }}
                      keycloak: {{ '{' }}
                          local: {{ '{' }}
                              url:      'http://localhost:8080',
                              realm:    'Xenon-Dev-DEV-ENV',
                              clientId: 'xenon-dev-oauth2-client-dev-env-id'
                              // No client secret — public PKCE client
                          {{ '}' }}
                      {{ '}' }}
                  {{ '}' }};

                  // keycloak.service.ts — initialise Keycloak before the Angular app bootstraps
                  @Injectable({{ '{' }} providedIn: 'root' {{ '}' }})
                  export class KeycloakInitService {{ '{' }}

                      constructor(private keycloak: KeycloakService) {{ '{' }}{{ '}' }}

                      init(): Promise<boolean> {{ '{' }}
                          return this.keycloak.init({{ '{' }}
                              config: {{ '{' }}
                                  url:      environment.localKeycloakURL,
                                  realm:    xenonDevConfig.keycloak.local.realm,
                                  clientId: xenonDevConfig.keycloak.local.clientId
                              {{ '}' }},
                              initOptions: {{ '{' }}
                                  onLoad:              'check-sso',   // don't force login on every page load
                                  silentCheckSsoRedirectUri:
                                      window.location.origin + '/assets/silent-check-sso.html'
                              {{ '}' }}
                          {{ '}' }});
                      {{ '}' }}
                  {{ '}' }}

The check-sso init option means the app silently checks whether the user already has an active Keycloak session (via an iframe) rather than redirecting them to the login page immediately. This gives the app a smooth experience — logged-in users land on the page they requested, while unauthenticated users see the public content until they explicitly choose to log in. Protected routes are guarded by an Angular CanActivate guard that checks the Keycloak token and redirects to the Keycloak login page if the token is absent or expired.
