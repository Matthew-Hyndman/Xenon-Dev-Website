Phase 1 completed

Phase 1 was where it all started. The objective was straightforward: build a functional, publicly deployed frontend that demonstrated real engineering decisions rather than a throw-away prototype. In this phase, I focused on establishing a solid foundation — learning how to deploy an Angular application through AWS Amplify, getting to grips with the Angular framework itself, and applying disciplined HTML, CSS, TypeScript, and JavaScript practices throughout. The entries below document the key tools and topics I worked through, the problems I encountered, and the decisions that shaped the production site you are reading now.

Choosing a deployment platform for Phase 1 required something that could handle a CI/CD pipeline without requiring a dedicated DevOps background to configure from scratch. AWS Amplify was the clear choice: it integrates directly with a GitHub repository, automatically rebuilds and deploys on every push to a tracked branch, and handles HTTPS, CDN distribution, and custom domain configuration out of the box.

Given that I had never used a hosting platform before, the setup process was a significant learning experience. The Amplify console walks you through connecting a repository, selecting a branch to track, and configuring the build settings. The defaults are a reasonable starting point, but they required several adjustments to work with the Angular project structure and build process. And at this point, I had not yet learned the principle of paying close attention to configuration details — which meant that the first few builds failed unexpectedly.

The setup process itself surfaced an important principle early on: the environment you deploy to is rarely identical to your local development environment. Node version mismatches and missing environment-specific settings caused the first several builds to fail before the pipeline was stable. Resolving this required pinning the Node version explicitly inside amplify.yml and aligning the build command with the Angular production configuration. Once those details were locked in, every subsequent push to the tracked branch deployed automatically without manual intervention — which is precisely the value of a well-configured pipeline.

Amplify also introduced me to the concept of separating branch environments. The main branch maps to the public-facing production site, while the Dev branch maps to a private preview environment — a pattern that was later formalised as part of the branching strategy described in the Phase 2 entry on GitHub team management tools.

amplify.yml is the build specification file that tells AWS Amplify exactly how to install, build, and package the application during each deployment. Without it, Amplify falls back to auto-detected defaults — which are rarely correct for a project with specific Node version requirements or custom build flags.

The version I arrived at after several failed builds looks like this: 

                  
                  version: 1
                  frontend:
                    phases:
                      preBuild:
                        commands:
                          - nvm use 20         # pin node version to match local dev
                          - npm ci             # clean install — reproducible builds
                      build:
                        commands:
                          - npm run build      # runs ng build --configuration production
                    artifacts:
                      baseDirectory: dist/amplify-angular-template-test/browser
                      files:
                        - '**/*'
                    cache:
                      paths:
                        - node_modules/**/*   # cache dependencies between builds

A few things are worth highlighting here. Using npm ci rather than npm install ensures that every build installs dependencies exactly as specified in package-lock.json, eliminating the risk of a dependency version drifting between deploys. The baseDirectory must point to the exact output folder Angular generates — getting this wrong produces a deployment that serves a blank page with no obvious error in the Amplify console. These were the kind of small but critical details that Phase 1 taught me to pay close attention to.

The native browser alert(), confirm(), and prompt() dialogs are functional but visually inconsistent with a polished frontend. SweetAlert2 replaces them with fully customisable, animated modal dialogs that can be styled to match the rest of the application. Integrating it into the Angular project was straightforward via NPM: 

                  
                  npm install sweetalert2

From there, calling a dialog is a single import and a promise-based API call: 

                  
                  import Swal from 'sweetalert2';

                  Swal.fire({{ '{' }}
                    title: 'Are you sure?',
                    text: 'This action cannot be undone.',
                    icon: 'warning',
                    showCancelButton: true,
                    confirmButtonText: 'Yes, proceed',
                    cancelButtonText: 'Cancel'
                  {{ '}' }}).then((result) => {{ '{' }}
                    if (result.isConfirmed) {{ '{' }}
                      // handle confirmation
                    {{ '}' }}
                  {{ '}' }});

Beyond aesthetics, SweetAlert2 encourages better UX habits. Replacing a raw confirm() with a styled dialog that clearly names the action being confirmed reduces the chance of a user dismissing a destructive prompt without reading it. It is a small detail, but it reflects the broader principle that production-quality UX is built from many small deliberate decisions.

HTML forms the structural backbone of every page on this site. While it is tempting to treat HTML as trivial — it is, after all, the starting point for most web developers — writing clean, semantic HTML has a measurable impact on accessibility, SEO, and the long-term maintainability of a project. Phase 1 reinforced a discipline of reaching for the correct semantic element rather than defaulting to <div> for everything.

In an Angular context, HTML templates also carry framework-specific responsibility. Data binding, event handling, structural directives, and component composition all live in the template layer. Getting comfortable with Angular's template syntax — particularly the distinction between property binding [property], event binding (event), and two-way binding [(ngModel)] — was an early focus that paid dividends throughout the rest of the phase.

One pattern that proved especially useful was decomposing pages into small, focused components with clear input and output contracts. This keeps individual templates short and readable, and it mirrors the separation of concerns principle that applies equally on the backend.

Animations are one of the areas where a site's perceived quality is most immediately felt. An abrupt transition between states — a button that changes colour in a single frame, a panel that appears instantaneously — reads as unfinished. Thoughtfully applied CSS animations and transitions smooth those state changes and give the interface a sense of responsiveness and physicality.

The approach used throughout this project relies primarily on CSS transition for hover states and simple property changes, and @keyframes for entrance and loading animations: 

                  
                  /* Smooth hover transition on nav links */
                  .nav-link {{ '{' }}
                    color: var(--text-secondary);
                    transition: color 0.2s ease, border-bottom 0.2s ease;
                  {{ '}' }}

                  .nav-link:hover {{ '{' }}
                    color: var(--accent);
                    border-bottom: 2px solid var(--accent);
                  {{ '}' }}

                  /* Entrance animation for page content */
                  @keyframes fadeSlideIn {{ '{' }}
                    from {{ '{' }}
                      opacity: 0;
                      transform: translateY(12px);
                    {{ '}' }}
                    to {{ '{' }}
                      opacity: 1;
                      transform: translateY(0);
                    {{ '}' }}
                  {{ '}' }}

                  .main-content {{ '{' }}
                    animation: fadeSlideIn 0.35s ease forwards;
                  {{ '}' }}

One discipline that Phase 1 established early was restraint. Animation should serve the user, not distract them. Every animation in this project has a duration of 0.35 seconds or less for interactive elements, and entrance animations are used sparingly — only where they reinforce the structure of the content rather than simply adding visual noise.

Layout is the most consequential CSS decision in any project. Getting it wrong produces pages that break on certain screen sizes, require excessive overrides to adjust, and become increasingly difficult to maintain as the component tree grows. Phase 1 established a consistent layout system built on CSS Flexbox and Grid, with a clear convention for when to use each.

Flexbox handles one-dimensional alignment — navigation bars, card rows, and any component where items need to be distributed along a single axis. Grid handles two-dimensional page structure — the overall page shell, multi-column content areas, and responsive section arrangements. Keeping this distinction consistent throughout the codebase prevents the situation where layout rules fight each other and produce unpredictable results at certain viewport sizes.

Responsive design was built in from the start rather than retrofitted. All layout breakpoints use relative units and clamp() where appropriate to allow fluid scaling between viewport sizes, reducing the number of explicit media queries needed to maintain a usable layout across devices. The result is a site that renders cleanly on both desktop and mobile without a separate mobile stylesheet.

JavaScript underpins every interactive behaviour on the frontend. In an Angular project, most of that logic is written in TypeScript — but a solid grounding in the JavaScript runtime is still essential. Angular's compilation model, change detection, and asynchronous data flows all depend on JavaScript fundamentals that are easy to overlook when working exclusively at the framework level.

Two areas received the most attention during Phase 1. The first was the event loop and asynchronous execution model — understanding why Promise callbacks and async/await behave differently from synchronous code, and how Angular's zone-based change detection interacts with asynchronous operations. The second was the module system: understanding the difference between ES modules and CommonJS, and how Angular's build pipeline resolves and bundles imports.

Working through these fundamentals made debugging significantly more productive. Rather than treating unexpected behaviour as framework magic, having a mental model of the runtime made it possible to reason about what was actually happening — which is ultimately the difference between guessing at a fix and understanding why it works.

TypeScript is the language Angular is written in and the language this project uses throughout the frontend. The core value it provides over plain JavaScript is static typing — the ability to describe the shape of data at compile time rather than discovering type errors at runtime in a user's browser. The practical effect is that a large class of bugs is caught before the application is ever deployed.

In Phase 1, the most immediate benefit was when working with API response shapes and component inputs. Defining an interface for each data structure the frontend handles means that typos in property names and incorrect assumptions about nullable fields are caught immediately by the compiler: 

                  
                  export interface NavLink {{ '{' }}
                    label: string;
                    route: string;
                    icon?: string;          // optional — not all links have icons
                    requiresAuth: boolean;
                  {{ '}' }}

                  // Any component consuming NavLink is guaranteed these properties exist.
                  // Accessing navLink.rout (a typo) is a compile error, not a runtime one.

The tsconfig.json configuration was also tuned during this phase. Enabling strict mode enforces the most useful group of type-checking options in a single flag — including strict null checks, which prevent the common mistake of treating a potentially-undefined value as though it is always defined. These constraints add a small amount of friction during initial development but significantly reduce the time spent debugging production issues.

angular.json is Angular's workspace configuration file. It defines build targets, asset paths, style inclusions, environment file mappings, and the configuration differences between development and production builds. Understanding it thoroughly — rather than treating it as boilerplate to leave untouched — was necessary early in Phase 1.

The most consequential section is the configurations block inside the build target. This is where the production build is given its environment file substitution, output hashing (for cache-busting on deploy), and bundle budget limits that warn or fail the build if the output exceeds a defined threshold: 

                  
                  "configurations": {{ '{' }}
                    "production": {{ '{' }}
                      "fileReplacements": [
                        {{ '{' }}
                          "replace": "src/environments/environment.ts",
                          "with": "src/environments/environment.prod.ts"
                        {{ '}' }}
                      ],
                      "outputHashing": "all",
                      "budgets": [
                        {{ '{' }}
                          "type": "initial",
                          "maximumWarning": "500kB",
                          "maximumError": "1MB"
                        {{ '}' }}
                      ]
                    {{ '}' }}
                  {{ '}' }}

The bundle budget configuration turned out to be directly useful: after adding a syntax highlighting library in Phase 2, the initial bundle exceeded the warning threshold. Because the budget was in place from Phase 1, the regression was surfaced at build time rather than discovered later through a slow user experience.

Jasmine is the testing framework Angular projects use by default for unit tests. It provides a behaviour-driven syntax that keeps tests readable and close to the language of requirements. Establishing a test suite early in Phase 1 was a deliberate decision — retrofitting tests onto an untested codebase is significantly harder than building the habit from the start.

The core pattern used throughout the project follows the Arrange, Act, Assert structure: set up the state, perform the operation, then verify the outcome: 

                  
                  describe('NavLinks', () => {{ '{' }}

                    it('should return only public links for an unauthenticated user', () => {{ '{' }}
                      // Arrange
                      const navLinks = new NavLinks();

                      // Act
                      const result = navLinks.getLinks(false);

                      // Assert
                      expect(result.every(link => !link.requiresAuth)).toBeTrue();
                    {{ '}' }});

                  {{ '}' }});

One lesson Phase 1 reinforced is that the value of a test suite is not simply having tests — it is having tests that actually fail when the code breaks. Writing tests that always pass regardless of implementation (for example, testing that a component renders without throwing, but nothing more) gives a false sense of coverage. Every test in this project is written to catch at least one specific regression.

NPM (Node Package Manager) is the dependency management tool for the Angular frontend. While it is straightforward to use at the surface level, understanding the distinction between its core concepts avoids a category of problems that tend to surface in CI/CD environments and collaborative codebases.

The most important discipline established in Phase 1 was the difference between npm install and npm ci. npm install resolves and updates package-lock.json if it diverges from package.json, which introduces the risk of a dependency version changing silently between environments. npm ci installs strictly from the lockfile and fails if any discrepancy exists — making it the correct choice for build pipelines where reproducibility is mandatory. The same logic applies to separating dependencies from devDependencies: test frameworks and build tools belong in devDependencies to prevent them from being included in the production bundle.

Keeping the dependency list lean is also an ongoing security practice. Every package added to the project is a potential attack surface. Running npm audit regularly and acting on high-severity findings before they accumulate was adopted as a habit during this phase — it is far easier to address vulnerabilities one at a time than to face a backlog of unresolved issues late in a project lifecycle.

This shift significantly improved the quality and predictability of my development process. Below is the branching strategy currently used in the project, reflecting the level of rigour I apply to code quality:

Dev – The last line of defence. Like main, it is linked to AWS and deployed via CI/CD, but the hosted site is not public-facing — it exists strictly for development and QA testing. Any feature destined for production is validated here first.

small-changes – Reserved for minor, low-risk changes that I want on production quickly without bypassing proper protocol.

Spring Security was a complex topic to learn and wrap my head around, but it is incredibly powerful when used correctly. I first encountered it through a Spring Boot course on Udemy by Chad Darby — and as a side note, Chad is a fantastic instructor if you're looking to get into full-stack development. Highly recommended.

The first learning curve was truly understanding what a filter chain is and what happens under the hood. A basic, bare-bones filter configuration would look something like this: 

                  
                  import org.springframework.context.annotation.Bean;
                  import org.springframework.context.annotation.Configuration;
                  import org.springframework.security.config.annotation.web.builders.HttpSecurity;
                  import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
                  import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
                  import org.springframework.security.web.SecurityFilterChain;

                  @Configuration // Marks this class as a source of bean definitions for the application context
                  @EnableWebSecurity // Enables Spring Security's web security support
                  public class SecurityConfig {{ '{' }}

                      @Bean // Indicates that this method produces a bean to be managed by the Spring container
                      public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {{ '{' }}

                          http
                              /* 
                                ---------------------------------------------------------------
                                  CSRF PROTECTION
                                  Enabled by default. Protects state-changing requests (POST,
                                  PUT, DELETE) from cross-site request forgery attacks by
                                  requiring a hidden token in forms.
                                  Disable only for stateless REST APIs (using JWTs, etc.).
                                ---------------------------------------------------------------
                              */ 
                              .csrf(AbstractHttpConfigurer::disable)

                              /*
                                  ---------------------------------------------------------------
                                    AUTHORIZATION RULES
                                    Processed by FilterSecurityInterceptor (or, in modern Spring
                                    Security, AuthorizationFilter) at the END of the chain.
                                    Rules are evaluated top-to-bottom — put specific rules first.
                                
                                    AnonymousAuthenticationFilter runs just before this block:
                                    if no auth has been set by the earlier filters, it assigns
                                    an "anonymous" token so the principal is never null.
                                  ---------------------------------------------------------------
                              */
                              .authorizeHttpRequests(requests -> requests
                                  // Public pages — anyone (including anonymous) can access
                                  .requestMatchers("/", "/welcome", "/css/**", "/js/**").permitAll()                

                                  // Any authenticated user (not anonymous)
                                  .anyRequest().authenticated()  
                                  
                              );            

                          return http.build(); // build the SecurityFilterChain

                          /*
                              Note: We don't configure CorsConfiguration, implement role-based 
                              access control, or any authentication, because those topics will be
                              demonstrated in other sections.
                          */
                      {{ '}' }}
                      
                  {{ '}' }}

On its own, the above configuration doesn't do a great deal. That said, these were the foundational concepts that gave me my first real foothold in both cybersecurity and Spring. But if Spring Security were limited to just that, it wouldn't have made it into this project. There is much more to it. Other key topics that fall under the Spring Security umbrella — and that are relevant to this project — include:

Filter Chains – Filter chains with their own unique rules, responses, and behaviours.
CORS (Cross-Origin Resource Sharing) – An essential component for any site that takes security seriously.
JWT (JSON Web Token) – The first grant type I got to grips with.
Role Authorisation – Something I am still deepening my understanding of, but which will be put to use in this project.

One of Spring Security's most valuable capabilities is the ability to define multiple, independent filter chains, each with distinct matchers, rules, and behavior. During this phase, I explored whether a custom filter was needed to address what I initially considered a security gap. At the time, I had recently improved my understanding of how bearer tokens relate to Keycloak sessions: the authorization code flow establishes authentication, and tokens are then presented on subsequent API requests. My concern was that I had not explicitly added backend token checks, so I investigated implementing manual validation inside a custom filter. 

                  
                  // 1. Create a custom filter by implementing the Filter interface
                  @Component
                  public class CustomFilter implements Filter {{ '{' }}
                  /* 
                      Filter interface is a part of the Java Servlet API and is used to 
                      perform filtering tasks on either the request to a resource, the 
                      response from a resource, or both.
                  */
                      private final Keycloak_Service_Impl keycloakService;
                      
                      public CustomFilter(Keycloak_Service_Impl keycloakService) {{ '{' }}
                          this.keycloakService = keycloakService;
                      {{ '}' }}

                      // doFilter method is where you implement the logic to validate the incoming request
                      @Override
                      public void doFilter(ServletRequest request, ServletResponse response, FilterChain filterChain)
                              throws IOException, ServletException {{ '{' }}

                          HttpServletRequest httpRequest = (HttpServletRequest) request;
                          HttpServletResponse httpResponse = (HttpServletResponse) response;

                          String token = httpRequest.getHeader("Token");

                          // Validate the incoming request
                          // If the token is missing or invalid, reject the request
                          // note: the actual validation logic should be implemented in the Keycloak_Service_Impl class        
                          if (token == null || !keycloakService.validateToken(token)) {{ '{' }}
                              httpResponse.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
                              httpResponse.setContentType("application/json");
                              httpResponse.getWriter().write("{{ '{' }}\"error\": \"Invalid or missing Token\"{{ '}' }}");
                              return; // tells the filter to stop here and not to continue with the filter chain 
                                      // (sends a 401 response back to the client)
                          {{ '}' }}

                          // Valid — pass the request along the filter chain
                          filterChain.doFilter(request, response);
                      {{ '}' }}
                  {{ '}' }}
                
              
                  
                    // 2. Register it in the Security Config
                    @Configuration
                    @EnableWebSecurity
                    public class SecurityConfig {{ '{' }}

                        @Autowired
                        private CustomFilter customFilter;

                        @Bean
                        public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {{ '{' }}
                            http
                                .csrf(csrf -> csrf.disable())
                                .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
                                .addFilterBefore(customFilter, UsernamePasswordAuthenticationFilter.class);

                            return http.build();
                        {{ '}' }}
                    {{ '}' }}

In conclusion, this investigation clarified an important design principle: custom filters should be introduced only when they add clear value beyond the framework's built-in capabilities. For standard JWT validation with Keycloak, Spring Security's resource server support already provides the required request protection. This investigation still proved useful, as it strengthened my understanding of filter ordering, authentication flow, and when custom security components are genuinely justified.

Cross-Origin Resource Sharing (CORS) became a critical topic as soon as the frontend and backend began communicating across different origins. While I had encountered CORS previously, the practical implementation became clear only after debugging browser errors during local integration. By default, the browser's same-origin policy blocks requests from one origin (for example, http://localhost:4200) to another (for example, http://localhost:8443/api) unless the server explicitly returns the correct CORS headers.

In Spring Security, CORS is processed before authentication filters. This ordering is essential because browsers send a preflight OPTIONS request before the actual request. That preflight must return 200 OK; if it is rejected with 401 Unauthorized, the browser blocks the call before the application logic is reached. The straightforward approach is to define CorsConfiguration in the security filter chain: 

                  
                  @Bean
                  public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {{ '{' }}
                      http
                              .csrf(csrf -> csrf.disable())
                              .authorizeHttpRequests(auth -> auth.anyRequest().permitAll());

                      CorsConfiguration corsConfig = new CorsConfiguration();

                      // Allowed origins — lock this down to real domains in production
                      corsConfig.setAllowedOrigins(List.of(
                              "http://localhost:4200" // Angular dev server
                      ));

                      // HTTP methods the browser is allowed to use
                      corsConfig.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));

                      // Headers the browser may send (Authorization carries the JWT)
                      corsConfig.setAllowedHeaders(List.of("Authorization", "Content-Type"));

                      // Allow the browser to read the Authorization header in responses
                      corsConfig.setExposedHeaders(List.of("Authorization"));

                      // Required when the frontend sends cookies or Authorization headers
                      corsConfig.setAllowCredentials(true);

                      // register the CORS configuration for all endpoints
                      http.cors(cors -> cors.configurationSource(request -> corsConfig));

                      return http.build();
                  {{ '}' }}

One early mistake was configuring allowedOrigins("*") together with allowCredentials(true). These settings are incompatible: when credentials are enabled, browsers reject wildcard origins. The correct solution is to specify explicit trusted origins per environment. Establishing this pattern also improved how environment-specific configuration is managed across the project.

Sensitive configuration is managed with environment variables, and local secrets are kept out of source control. This approach aligns with best practice by preventing accidental exposure of credentials and server configuration details.

JSON Web Tokens (JWTs) are the mechanism the project uses to prove identity across the boundary between the Angular frontend, the Spring Boot API, and Keycloak. A JWT is a compact, URL-safe string made up of three Base64URL-encoded parts separated by dots: a header (algorithm metadata), a payload (claims about the user), and a signature (cryptographic proof that the token hasn't been tampered with).

In this project, Keycloak issues the tokens. The Angular app obtains an access token after the user logs in and attaches it to every API request as a Bearer token in the Authorization header. The Spring Boot resource server then validates the token without contacting Keycloak on every request — it does this by fetching Keycloak's public keys from the JWKS endpoint once and caching them locally. Configuring the resource server requires only a single property pointing at the issuer URI: 

                  
                  # application.properties
                  spring.security.oauth2.resourceserver.jwt.issuer-uri=\
                      http://localhost:8080/realms/Xenon-Dev-DEV-ENV

                  # Spring auto-discovers the JWKS URI from the issuer's
                  # OpenID Connect discovery document at:
                  # {{ '{' }}issuer-uri{{ '}' }}/.well-known/openid-configuration

On the Spring side, enabling JWT validation in the filter chain is then just one line: 

                  
                  .oauth2ResourceServer(oauth2 -> oauth2
                      .jwt(jwt -> jwt
                          // Optional: customise how claims are mapped to Spring's
                          // GrantedAuthority list (e.g. extracting Keycloak realm roles)
                          .jwtAuthenticationConverter(keycloakJwtAuthenticationConverter())
                      )
                  )

One thing worth noting is that JWTs are stateless. The server never stores them — which means revoking a token before it expires requires extra work (a token blacklist or short expiry windows). For this project I settled on short-lived access tokens (5 minutes) combined with Keycloak's refresh token flow, which strikes a reasonable balance between security and usability.

A foundational principle of secure backend development is that secrets must never be embedded in source code. Despite how self-evident this may appear, it is a surprisingly common mistake to include a database password or API key directly in an application.properties file and commit it to version control. A deliberate configuration strategy was established from the outset of the Xenon Dev project to prevent this entirely.

The approach is layered. In local development, sensitive values are stored in an application-local.properties file that is listed in .gitignore and excluded from all commits. Spring Boot is configured to activate the local profile automatically during development, resolving these values without requiring any modifications to tracked files. In deployed environments, credentials are provided exclusively as environment variables injected by AWS, keeping them entirely outside the repository: 

                  
                  # application.properties (committed — no secrets here)
                  spring.datasource.url=${DB_URL}
                  spring.datasource.username=${DB_USERNAME}
                  spring.datasource.password=${DB_PASSWORD}

                  keycloak.client-secret=${KEYCLOAK_CLIENT_SECRET}                  

                  # -----------------------------------------------------------
                  # application-local.properties (git-ignored — secrets live here locally)
                  # -----------------------------------------------------------
                  # spring.datasource.url=jdbc:mysql://localhost:3306/xenon_dev
                  # spring.datasource.username=root
                  # spring.datasource.password=supersecret
                  # keycloak.client-secret=abc123...

The Keycloak client secret warrants particular attention. In OAuth2, the client secret is the credential the backend presents to Keycloak when exchanging an authorisation code for a token, or when authenticating via the client credentials flow for service-to-service communication. Exposure of this value would allow an attacker to impersonate the backend application entirely. It is therefore treated with the same rigour as a database password: stored outside version control.

Designing a robust REST API requires more rigor than it may initially appear. Early endpoint implementations were functional, but lacked consistency, were difficult to document, and introduced unnecessary complexity for the Angular frontend. Refactoring the API around established RESTful conventions significantly improved maintainability and long-term scalability.

The core principle is that URLs represent resources (nouns), not actions (verbs). HTTP methods define the action semantics. The following example shows the controller structure used for the user resource in this project: 

                  
                  @RestController
                  @RequestMapping("/api/users")
                  public class UserController {{ '{' }}

                      // GET /api/users          — list all users (paginated)
                      @GetMapping
                      public Page<UserDTO> getUsers(Pageable pageable) {{ '{' }}
                          return userService.findAll(pageable);
                      {{ '}' }}

                      // GET /api/users/{id}    — get a single user by ID
                      @GetMapping("/{id}")
                      public UserDTO getUser(@PathVariable Long id) {{ '{' }}
                          return userService.findById(id);
                      {{ '}' }}

                      // POST /api/users         — create a new user
                      @PostMapping
                      @ResponseStatus(HttpStatus.CREATED) // 201 Created, not 200 OK
                      public UserDTO createUser(@RequestBody @Valid CreateUserRequest request) {{ '{' }}
                          return userService.create(request);
                      {{ '}' }}

                      // PUT /api/users/{id}    — replace a user (idempotent)
                      @PutMapping("/{id}")
                      public UserDTO updateUser(@PathVariable Long id,
                                               @RequestBody @Valid UpdateUserRequest request) {{ '{' }}
                          return userService.update(id, request);
                      {{ '}' }}

                      // DELETE /api/users/{id} — remove a user
                      @DeleteMapping("/{id}")
                      @ResponseStatus(HttpStatus.NO_CONTENT) // 204, no body
                      public void deleteUser(@PathVariable Long id) {{ '{' }}
                          userService.delete(id);
                      {{ '}' }}
                  {{ '}' }}

Several conventions are applied consistently across the API: return DTOs rather than exposing JPA entities directly, use explicit and appropriate HTTP status codes (201 for created resources, 204 for deletions, and 404 with a consistent error payload for missing resources) from the outset.

Debugging a REST API involves a different mindset to debugging a monolithic application. The problem could be anywhere in the chain: the Angular HTTP client, the network, the Spring Security filter, the controller, the service, or the database. Over the course of building this project I built up a systematic approach to narrowing down where things are going wrong quickly.

My primary tool is Postman. By firing requests directly at the API (bypassing the Angular app entirely), I can immediately eliminate the frontend as the source of the problem. Postman also handles OAuth2 flows natively, so I can obtain a real Keycloak token and attach it to requests without writing a single line of code.

Another tool I use is the browser's built-in developer tools, particularly the Network tab. This allows me to inspect the raw HTTP requests and responses, including headers, status codes, and payloads. Identity and Access Management (IAM) is the discipline of deciding who can do what on which resource. In this project, IAM is implemented through a combination of Keycloak (which handles authentication and issues JWTs carrying identity claims) and Spring Security (which enforces authorisation rules on each endpoint based on those claims).

The critical bridge between the two is the JWT authentication converter. Keycloak encodes the user's roles inside the token under a non-standard claim path (realm_access.roles), whereas Spring Security expects GrantedAuthority objects prefixed with ROLE_. Without a custom converter, Spring simply wouldn't see any roles in the token and would deny every role-restricted endpoint. The converter unwraps the Keycloak claim and maps it to Spring's format: 

                  
                  @Component
                  public class KeycloakJwtAuthenticationConverter
                          implements Converter<Jwt, AbstractAuthenticationToken> {{ '{' }}

                      private final JwtGrantedAuthoritiesConverter defaultConverter =
                          new JwtGrantedAuthoritiesConverter();

                      @Override
                      public AbstractAuthenticationToken convert(Jwt jwt) {{ '{' }}
                          // Extract standard scopes (e.g. SCOPE_openid) via the default converter
                          Collection<GrantedAuthority> authorities =
                              new ArrayList<>(defaultConverter.convert(jwt));

                          // Extract Keycloak realm roles from realm_access.roles
                          Map<String, Object> realmAccess =
                              jwt.getClaimAsMap("realm_access");

                          if (realmAccess != null && realmAccess.containsKey("roles")) {{ '{' }}
                              List<?> roles = (List<?>) realmAccess.get("roles");
                              roles.stream()
                                  .map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                                  .forEach(authorities::add);
                          {{ '}' }}

                          return new JwtAuthenticationToken(jwt, authorities,
                              jwt.getClaimAsString("preferred_username"));
                      {{ '}' }}
                  {{ '}' }}

With this converter in place, the JWT arriving from Keycloak is fully understood by Spring Security. Downstream, the controller can use standard Spring annotations such as @PreAuthorize("hasRole('ADMIN')") to enforce fine-grained access control, and the identity of the authenticated user is available anywhere in the request via the SecurityContextHolder — without any additional calls to Keycloak.

Role-based access control (RBAC) is the layer on top of authentication that answers the question: "this user is who they say they are — but are they allowed to perform this action?" In this project, roles are defined in Keycloak and embedded in the JWT, then enforced in Spring Security at both the HTTP layer (filter chain rules) and the method layer (@PreAuthorize annotations).

The project currently defines three roles: USER (standard authenticated user), MODERATOR (elevated read access and the ability to manage content), and ADMIN (full access including user management endpoints). Applying these rules at the filter chain level covers the coarse-grained cases, while @PreAuthorize handles fine-grained method-level security: 

                  
                  // --- Filter chain (coarse-grained) ---
                  .authorizeHttpRequests(auth -> auth
                      .requestMatchers(HttpMethod.GET, "/api/**").hasAnyRole("USER", "MODERATOR", "ADMIN")
                      .requestMatchers("/api/admin/**").hasRole("ADMIN")
                      .requestMatchers("/api/moderation/**").hasAnyRole("MODERATOR", "ADMIN")
                      .anyRequest().authenticated()
                  )

                  // --- Method-level (fine-grained) ---
                  @Service
                  public class UserManagementService {{ '{' }}

                      // Only admins can delete users
                      @PreAuthorize("hasRole('ADMIN')")
                      public void deleteUser(Long userId) {{ '{' }}
                          userRepository.deleteById(userId);
                      {{ '}' }}

                      // A user can read their own profile; an admin can read any profile
                      @PreAuthorize("hasRole('ADMIN') or #username == authentication.name")
                      public UserDTO getProfile(String username) {{ '{' }}
                          return userRepository.findByUsername(username)
                              .map(userMapper::toDTO)
                              .orElseThrow(() -> new ResourceNotFoundException("User not found"));
                      {{ '}' }}
                  {{ '}' }}

The @PreAuthorize expression on getProfile above demonstrates Spring's SpEL-based security expressions. The #username == authentication.name clause binds the method parameter to the currently authenticated principal — a clean way to enforce ownership rules without writing any conditional logic inside the method body itself. Enabling method security requires adding @EnableMethodSecurity to the security configuration class.

Spring Data JPA repositories were one of the features that made me genuinely appreciate the Spring ecosystem. At its simplest, a JPA repository is an interface that Spring implements at runtime — you declare the methods you need and Spring writes the SQL for you. No boilerplate, no manual connection management, no result-set mapping.

Player_ProfileRepo is a good example of where the repository abstraction stays useful even when the query is no longer a simple entity lookup. The interface still extends JpaRepository<Player_Profile, Long>, so it inherits the standard CRUD methods, but it also adds a custom native query for the leaderboard endpoint: 

                  
                    @RepositoryRestResource
                    public interface Player_ProfileRepo extends JpaRepository<Player_Profile, Long> {{ '{' }}

                      @Query(
                            value = "SELECT USERNAME, wins, losses, pot " +
                                    "FROM accounts_with_player_profiles_view " +
                                    "ORDER BY pot DESC, wins DESC",
                            countQuery = "SELECT COUNT(*) FROM accounts_with_player_profiles_view",
                          nativeQuery = true
                      )
                        Page<Object[]> getAccountsWithPlayerProfiles(Pageable pageable);
                  {{ '}' }}

The key point here is that the leaderboard data does not come directly from a single JPA entity table. Instead, the query reads from accounts_with_player_profiles_view, a database view that already joins and shapes the account and player profile data into the exact projection needed by the frontend. That keeps the SQL centralised in one place and avoids repeating the same join logic across controllers or services.

Returning Page<Object[]> rather than a full entity is a deliberate trade-off. The query only needs four columns for the leaderboard — username, wins, losses, and pot — so pulling back a raw projection is lighter than hydrating a full entity graph. The separate countQuery is also important: without it, Spring Data would not know how to calculate the total number of rows for pagination metadata. In practice, this gives the Angular frontend a leaderboard result set that is already sorted by pot first and wins second, while still supporting pageable API responses.

A Data Transfer Object (DTO) is a plain object whose sole purpose is to carry data between layers of the application. In the context of this project, DTOs sit between the JPA entities (which mirror the database schema) and the REST API (which defines the public contract). This separation solves several real problems at once: it prevents accidentally exposing sensitive fields, it decouples the API contract from the database schema, and it gives a natural place to put input validation annotations.

In the leaderboard flow, DTOs are used as an output contract for aggregated data that does not map cleanly to a single JPA entity. The repository returns each row as Object[] from a native SQL view query, and the service maps those positional columns into a typed Leader_Board_DTO before returning the response: 

                  
                  @Getter
                  @Setter
                  @AllArgsConstructor
                  public class Leader_Board_DTO {{ '{' }}
                      private String USERNAME;
                      private int wins;
                      private int losses;
                      private int pot;
                  {{ '}' }}

                  @Override
                  public Page<Leader_Board_DTO> getAccountsWithPlayerProfiles_view(Pageable pageable) {{ '{' }}
                      Page<Object[]> results = playerProfileRepo.getAccountsWithPlayerProfiles(pageable);
                      return results.map(row -> new Leader_Board_DTO(
                          (String) row[0],
                          (Integer) row[1],
                          (Integer) row[2],
                          (Integer) row[3]
                      ));
                  {{ '}' }}

                  @GetMapping("leaderboard")
                  public ResponseEntity<Page<Leader_Board_DTO>> getleaderboard(
                      @RequestParam(defaultValue = "0") int page,
                      @RequestParam(defaultValue = "10") int size
                  ) {{ '{' }}
                      Pageable pageable = PageRequest.of(page, size);
                      return ResponseEntity.ok(playerService.getAccountsWithPlayerProfiles_view(pageable));
                  {{ '}' }}

This pattern keeps the native SQL details isolated to the repository and service, while the controller exposes a stable, paginated DTO response to the frontend. It also makes future refactoring safer: if the underlying view changes, the API contract can remain unchanged as long as the service mapping still builds the same DTO fields.

A MySQL view is a stored SELECT statement that acts like a virtual table. Querying a view looks identical to querying a real table, but the data is assembled on the fly from the underlying tables when the view is accessed. I introduced views in this project for two reasons: to simplify complex recurring queries that appeared in multiple places, and to provide a read-only, security-trimmed projection of data that could be exposed more freely than the raw tables.

A practical example in this project is accounts_with_player_profiles_view, which powers the leaderboard endpoint. Instead of joining user_entity and player_profile in every repository query, the join is defined once in the view and reused as a stable read model: 

                  
                  CREATE
                      ALGORITHM = UNDEFINED
                      DEFINER = `xenondev`@`localhost`
                      SQL SECURITY DEFINER
                  VIEW `accounts_with_player_profiles_view` AS
                  SELECT
                      ue.USERNAME AS USERNAME,
                      pp.wins     AS wins,
                      pp.losses   AS losses,
                      pp.pot      AS pot
                  FROM user_entity ue
                  JOIN player_profile pp
                      ON ue.PLAYER_PROFILE_ID = pp.player_id;

                  -- Consumed by the leaderboard repository query
                  SELECT USERNAME, wins, losses, pot
                  FROM accounts_with_player_profiles_view
                  ORDER BY pot DESC, wins DESC;

On the Spring side, this view is queried through a native repository method that returns Page<Object[]>, then mapped in the service layer to Leader_Board_DTO for the API response. That keeps SQL shaping in the database, data access in the repository, and response shaping in the service. The result is a clean, paginated leaderboard payload with username, wins, losses, and pot already sorted in rank order.

A MySQL trigger is a piece of SQL that the database engine executes automatically in response to an INSERT, UPDATE, or DELETE on a specified table. Triggers enforce data integrity rules at the database level — meaning they fire regardless of which application, service, or tool modifies the data. This makes them a reliable safety net for invariants that must always hold.

In this project, the trigger is used to keep related user and player-profile data consistent during hard deletes. The trigger runs before a row is deleted from user_entity and removes the linked player_profile row using the old PLAYER_PROFILE_ID value: 

                  
                  CREATE DEFINER=`xenondev`@`localhost`
                  TRIGGER `xenondevdb`.`user_entity_BEFORE_DELETE`
                  BEFORE DELETE ON `user_entity`
                  FOR EACH ROW
                  BEGIN
                      DELETE FROM `xenondevdb`.`player_profile`
                      WHERE OLD.PLAYER_PROFILE_ID = `player_profile`.`player_id`;
                  END

The practical effect is application-level cascade cleanup at the database layer: deleting a user also deletes that user's profile record, preventing orphaned rows in player_profile. Because this logic runs in the database engine, it applies consistently no matter whether the delete originates from Spring, a script, or a direct SQL client.

Keycloak is the identity provider at the heart of the project's authentication architecture. It handles user registration, login, token issuance, token refresh, and logout — offloading all of that complexity from the application itself. Instead of building and maintaining a custom auth system (with all the security risks that entails), the Spring Boot backend acts purely as a resource server that trusts the JWTs that Keycloak signs.

Setting up Keycloak for this project involved creating a realm (a namespace for users and clients), registering the Angular app and the Spring Boot API as separate clients, and defining the realm roles that map to the application's access control model. The Angular client uses the Authorization Code + PKCE flow — the most secure flow for public clients (browser apps that cannot safely store a client secret): 

                  
                  // xenon-dev-config.ts — Keycloak connection settings (Angular)
                  export default {{ '{' }}
                      keycloak: {{ '{' }}
                          local: {{ '{' }}
                              url:      'http://localhost:8080',
                              realm:    'Xenon-Dev-DEV-ENV',
                              clientId: 'xenon-dev-oauth2-client-dev-env-id'
                              // No client secret — public PKCE client
                          {{ '}' }}
                      {{ '}' }}
                  {{ '}' }};

                  // keycloak.service.ts — initialise Keycloak before the Angular app bootstraps
                  @Injectable({{ '{' }} providedIn: 'root' {{ '}' }})
                  export class KeycloakInitService {{ '{' }}

                      constructor(private keycloak: KeycloakService) {{ '{' }}{{ '}' }}

                      init(): Promise<boolean> {{ '{' }}
                          return this.keycloak.init({{ '{' }}
                              config: {{ '{' }}
                                  url:      xenonDevConfig.keycloak.local.url,
                                  realm:    xenonDevConfig.keycloak.local.realm,
                                  clientId: xenonDevConfig.keycloak.local.clientId
                              {{ '}' }},
                              initOptions: {{ '{' }}
                                  onLoad:              'check-sso',   // don't force login on every page load
                                  silentCheckSsoRedirectUri:
                                      window.location.origin + '/assets/silent-check-sso.html'
                              {{ '}' }}
                          {{ '}' }});
                      {{ '}' }}
                  {{ '}' }}

The check-sso init option means the app silently checks whether the user already has an active Keycloak session (via an iframe) rather than redirecting them to the login page immediately. This gives the app a smooth experience — logged-in users land on the page they requested, while unauthenticated users see the public content until they explicitly choose to log in. Protected routes are guarded by an Angular CanActivate guard that checks the Keycloak token and redirects to the Keycloak login page if the token is absent or expired.

Phase 2.1 was a follow-up phase focused on backend revision and redesign. During the deployment of Phase 2, it became clear that the backend architecture was expensive to set up and use. As EC2 and RDS instances had to be running 24/7 to support the application, the cost of hosting was much higher than anticipated for a project of this scale.

Noting The cost of $45 a month for hosting the backend on AWS EC2 and RDS for just one environment was unsustainable for a personal project, and the architecture, I looked for a more cost-effective and scalable solution. The decision was made to refactor the backend to use AWS Amplify configuration for authentication and data storage. This serverless architecture significantly reduces hosting costs, as resources are only consumed when APIs are invoked to AWS Lambda, and it also simplifies scaling and maintenance.

This Amplify-based architecture is just a temporary solution to keep hosting costs manageable while I research and learn about more sustainable backend architectures for personal projects. The main goal of this phase was to implement a functional backend that supports the core features/requirements of the application, while keeping costs low and allowing for future iteration, improvement and effective use.

Since I have an enterprise-level backend that uses Keycloak and Spring Boot and is fully functional, I want to try another method of deployment that is cost-effective.

The first step in the Phase 2.1 backend redesign was establishing an AWS Amplify Gen 2 backend directly in the repository so infrastructure and application logic could be versioned together. Instead of manually wiring Cognito, AppSync, and data access rules in separate consoles, the backend is defined as TypeScript resources under amplify/, which makes the architecture easier to reason about, review, and evolve.

Authentication was configured with Cognito user pools using email login and explicit user attributes that match account profile requirements in the app. In particular, preferredUsername, givenName, and familyName are marked required and mutable, so the account data needed by the frontend is present from signup while still allowing user-driven profile updates. 

                  
                  // amplify/auth/resource.ts
                  export const auth = defineAuth({{ '{' }}
                    loginWith: {{ '{' }}
                      email: true,
                    {{ '}' }},
                    userAttributes: {{ '{' }}
                      preferredUsername: {{ '{' }} required: true, mutable: true {{ '}' }},
                      givenName: {{ '{' }} required: true, mutable: true {{ '}' }},
                      familyName: {{ '{' }} required: true, mutable: true {{ '}' }},
                    {{ '}' }},
                  {{ '}' }});

Data modelling was then implemented using Amplify Data with a PlayerProfile model. The schema defines a stable identifier (player_id) and the game metrics required for leaderboard and profile features (wins, losses, and pot) with sensible defaults. This keeps new records predictable and avoids null-heavy edge cases in the UI. 

                  
                  // amplify/data/resource.ts
                  const schema = a.schema({{ '{' }}
                    PlayerProfile: a
                      .model({{ '{' }}
                        player_id: a.id().required(),
                        username: a.string().required(),
                        wins: a.integer().default(0),
                        losses: a.integer().default(0),
                        pot: a.integer().default(3000),
                      {{ '}' }})
                      .identifier(['player_id'])
                      .authorization((allow) => [
                        allow.owner(),
                        allow.authenticated().to(['read']),
                      ]),
                  {{ '}' }});

                  export const data = defineData({{ '{' }}
                    schema,
                    authorizationModes: {{ '{' }}
                      defaultAuthorizationMode: 'userPool',
                    {{ '}' }},
                  {{ '}' }});

The authorisation strategy here is intentionally split: owners can fully manage their own data, while any authenticated user can read records where needed for shared features. With userPool as the default auth mode, access is consistently anchored to Cognito identity. The result is a backend setup that is lightweight, cost-aware, and fast to iterate on, while still enforcing clear security boundaries in code.

AWS Cognito is the user authentication and management service used in the Phase 2.1 backend redesign. It provides a scalable, secure, and fully managed solution for handling user sign-up, sign-in, and access control without the need to build a custom authentication system from scratch.
